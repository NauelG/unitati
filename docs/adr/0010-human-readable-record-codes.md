# 0010. Human-readable record codes, from a sequence, editable, in the URL

- **Status:** accepted
- **Date:** 2026-10-07

## Context

Every screen in the design system identifies records by a short code, never by a key:
`AST-0142`, `TCK-1093`, `PRJ-012`. `RecordRef` — _"the visual unit of unitati's core idea"_ —
takes an `id` of that shape, `DataTable` puts it in the first column, and `GlobalSearch`
promises that _"typing an exact ID jumps straight to it on Enter"_.

The schema has only UUIDs. Nothing generates these codes, and four entities need them: assets,
tickets, projects and tasks.

Two facts constrain the answer, and they pull in opposite directions.

**The code is physical.** [Issue #22](../../../issues/22) prints it on a label and sticks it on
hardware; [#23](../../../issues/23) resolves a found asset by scanning that label;
[#24](../../../issues/24) walks a room scanning them. Once printed, the code is on a machine in
a corridor and changing it in software does not change the sticker.

**The code pre-exists.** [Issue #21](../../../issues/21) imports a Snipe-IT or Shelf export,
and those carry asset tags the organisation has been using for years — already on the hardware.
A system that generates its own codes on import ends up calling `AST-0142` a machine whose
sticker says something else.

## Decision

**One code per record, generated, editable, and the public identifier.**

- **Generated by a Postgres sequence per entity type**, rendered as a fixed uppercase prefix
  plus a zero-padded number: `AST-`, `TCK-`, `PRJ-`, `TSK-`.
- **Stored in a single column**, unique per organisation, **editable**. The generated value is
  a default, not a constant. Renaming changes the record's URL; the MVP ships no redirect.
- **The URL identifier**: `/assets/AST-0142`, not `/assets/<uuid>`. The UUID remains the primary
  key and the target of every foreign key.
- **Prefixes are fixed in code**, not configurable. [ADR 0007](0007-roles-and-permissions.md)
  established that structure is not externalised; a prefix is structure.
- **Codes are flat.** A subtask carries its own `TSK-####` from the same sequence, never
  `TSK-0045.1`.

## Consequences

- An import can keep the codes already stuck to the hardware, because the column is editable.
  A generated-only code would have forced a second field later, and a second field means
  explaining on every screen which of the two codes someone means.
- Counting rows to produce the next number — the obvious shortcut — is wrong under deletion and
  under concurrency. A sequence is correct under both and costs nothing.
- **A single global sequence per type is a conscious debt.** The correct shape once
  [#42](../../../issues/42) brings active multi-tenancy is a counter per organisation. With one
  organisation the two produce identical numbers, so the debt is invisible today and the
  migration is a backfill, not a redesign. It is written here so the next reader finds it
  deliberate rather than overlooked.
- Editing a code changes the URL and breaks links already pasted into chats. Accepted: the
  alternative is an immutable code the organisation cannot reconcile with its own labels, and a
  link that 404s is a smaller harm than an inventory that disagrees with its stickers.
- Flat subtask codes survive promotion and reparenting. `TSK-0045.1` stops being true the moment
  the subtask is promoted or moved under a different parent — and then the identifier someone
  pasted into a chat points at something else. A subtask _is_ a task; the hierarchy is a relation
  between tasks, not part of their identity.
- `GlobalSearch`'s exact-ID shortcut resolves through the same permission scope as any other
  query. A code that jumps for a record the user may not see confirms that the record exists,
  which is the leak a "no permission" message also commits.

## Alternatives considered

- **Two fields: an immutable `code` for the URL and an editable `asset_tag` for the label.**
  Rejected: two identifiers for the same thing must be explained everywhere they appear, and
  nobody ever remembers which is which. One editable field covers both needs.
- **Numbering within the parent** (`PRJ-012-4` for a task). Rejected: it needs a per-project
  counter with its own concurrency race, and it stops being true as soon as a task moves between
  projects.
- **UUIDs in the URL.** Rejected: it contradicts the design system, which puts a mono-spaced
  short code in the first column of every table, and it defeats the thing codes are for — being
  pasteable into a sentence.
- **Configurable prefixes.** Rejected as catalogue masquerading as configuration, per ADR 0007.
- **Row count as the next number.** Rejected: incorrect under deletion and under concurrency.

## Amendment 2026-10-18: page codes are not editable

Knowledge-base pages carry a `DOC-####` code from their own sequence, in the URL like every other
record, but **the code cannot be edited** ([ADR 0031](0031-knowledge-base-spaces-page-tree-and-revisions.md)).
Editability exists here for two reasons, both physical: the code is printed on a label, and an
import brings codes the organisation already uses. Neither applies to a page. What does apply is
that pages link to one another by code, inside their content, so a renamed code would break every
page that points at it, and no redirect exists to save them.
