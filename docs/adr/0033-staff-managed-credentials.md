# 0033. Credentials are granted by staff with a temporary password

- **Status:** accepted
- **Date:** 2026-10-19

## Context

Until #230 the only credential that could exist was the first admin's, created by `/setup`. Everyone
else in the directory (ADR 0007: roles live on `users`) was a record with no way to sign in. Mail is
optional (ADR 0006), so invitation links cannot be the mechanism, and SSO and SCIM (#43) are still
pending.

## Decision

1. **The admin creates the credential**, with a **temporary password generated by the system**: 16
   characters from `crypto.getRandomValues` over an alphabet without look-alikes (rejection sampling,
   so no character is likelier than another). It is shown **once**, with a copy button, and is never
   stored in plain text or logged.
2. **The role is chosen when access is granted**, not when the person is created, and can be changed
   later.
3. **`users.must_change_password`** is true after a grant or a reset. While it is, `hooks.server.ts`
   redirects every request (except `/account/password`, `/sign-out`, `/api/auth`, `/_app/` assets and
   `/api/v1`, whose API keys are not sessions) to `/account/password`, in the `(auth)` group for its
   bare layout. The page is also the voluntary change, from the user menu.
4. **Better Auth's admin plugin is not adopted.** It would add a second source of truth for roles
   (ADR 0007), its own ban model next to the directory's `active`, and impersonation we do not want.
5. **The credential is written by us, in our transaction, using Better Auth only for the password
   hasher** (`(await getAuth().$context).password.hash`). The alternative, `signUpEmail` followed by
   deleting the session it creates, leaves a window in which the new user holds a session, and it
   cannot be rolled back together with the role and the `people.user_id` link. Inserting the `users`
   and credential `auth_accounts` rows ourselves makes grant atomic and sessionless. The shape of the
   rows is Better Auth's (`provider_id = 'credential'`, `account_id = user id`); the specs sign in
   through Better Auth to prove it still accepts them.
6. **Reset** hashes a new temporary password, sets the flag and deletes the user's sessions.
7. **Revoke** deletes the `users` row. Sessions and credential cascade, `people.user_id` becomes
   null, and the person stays.
8. **Guards:** the last active admin (an admin whose person is active in the organisation) cannot be
   demoted or revoked, and an admin cannot demote or revoke themselves.
9. **Deactivation blocks sign-in.** The `auth` domain deactivates the person through the directory
   and deletes the user's sessions; `resolveSessionUser` ignores a user whose person is inactive, so
   a lingering session resolves to nobody; sign-in is refused after the password is verified, so the
   message does not reveal which addresses exist. Reactivation restores it.
10. **The email of a person with access changes in `users` and `people` in one transaction**
    (`changeAccessEmail`, through directory functions that accept the transaction, ADR 0002).

## Consequences

- An admin must hand the temporary password over through some other channel. That is the cost of not
  depending on mail; a later "forgot password" flow can use it when SMTP is configured.
- `SessionUser.mustChangePassword` is optional: API-key and service-account users have no password.
- Roles change on the user's next request, because the session user is resolved from the database
  on every request.

> **Note (ADR 0056):** a person who signs in through the identity provider needs no grant: the IdP
> decides access and Unitati creates their user as `employee`. While SSO is required, "Grant access"
> and "Reset password" are offered only for admins, and the address of a linked person is managed by
> the provider (it is read-only until an admin unlinks them).
