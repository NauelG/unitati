# 0048. Module boundaries are enforced by dependency-cruiser

- **Status:** accepted
- **Date:** 2026-10-23
- **Issue:** [#353](../../../issues/353)

## Context

[ADR 0002](0002-server-modules-by-domain.md) draws the module boundaries and
[ADR 0024](0024-in-process-domain-events.md), [ADR 0009](0009-activity-log.md) and
[ADR 0040](0040-transactional-notifications.md) refine them. Until now four overlapping
`no-restricted-imports` blocks in `eslint.config.js` enforced them for `projects`, `notifications`,
`imports` and (since #349) `links` only. That had four defects:

- **Blocks replace each other.** In flat config a later block for the same files replaces the
  earlier `no-restricted-imports` setting, so every block had to repeat the notifications pattern.
  A `links` → `assets` tables violation grew unnoticed that way.
- **The rules matched import text, not resolved files.** Imports come as relative paths and as
  `#lib/…/x.js` (which resolves to `x.ts`); a regex has to guess both.
- **Barrels re-exported tables as values.** `import { tickets } from '../service-desk'` looks
  exactly like a function import to a file-level rule. A hand-maintained `BARREL_TABLES` list
  papered over it for `links` alone.
- **No graph rule.** Nothing detected a cycle, and the CI lint cache relints only changed files,
  while a cycle can be closed from a file that did not change.

## Decision

[dependency-cruiser](https://github.com/sverweij/dependency-cruiser) checks the whole resolved
import graph on every run. Its rules live in `.dependency-cruiser.cjs`, one rule per decision, each
commenting the ADR behind it. `npm run lint` runs it first (`lint:boundaries`: `--ignore-known`, no
cache), then prettier, then eslint. All rules are `error` and count `import type` edges, except
where stated.

### Module classes

- **Business modules:** `assets`, `service-desk`, `projects`, `knowledge`, `links`, `directory`,
  `activity`, `notifications`, `imports`, `search`, `api`, `seed`, `screens` (ADR 0050).
- **Infrastructure:** `auth`, `access`, `db`, `shared`, `settings`.
- **Root files** of `src/lib/server/` (`subscriptions.ts`, `ports.ts`) are composition code and follow the
  rules for code outside a module.

ADR 0002 says every domain may depend on `directory`. That includes `directory`'s tables, and
`auth`'s: `directory/schema.ts` and `auth/schema.ts` are the shared kernel, open to every server
module. Closing them (functions only) would touch 30+ files and is not decided here.

### Rules

1. **Public entry** (`public-entry-from-outside`, `public-entry-across-modules`). From outside a
   business module only its `index.ts` (and its `schema.ts`, judged by rule 2) may be imported.
   Any root file of an infrastructure module is public; its subfolders are not.
2. **Tables** (`tables-from-module`, `tables-from-outside`). A `<m>/schema.ts` is imported only
   from its own module, from `db/schema.ts`, from another module's `schema.ts` (foreign keys) and
   from `activity` and `notifications` (the records they point at). `imports`, `search`, `seed`,
   `api`, the routes and every other consumer import no other module's `schema.ts`, except the
   open `directory` and `auth`.
3. **Barrels carry no tables** (`barrel-carries-no-tables`, plus `barrels.spec.ts`). A business
   module's `index.ts` re-exports no `pgTable`, enum or sequence as a value; row types
   (`export type`) stay. A consumer that needs a table imports `<m>/schema` and is judged by
   rule 2. dependency-cruiser sees the edge, not the names, so the spec checks the actual exports
   of every barrel.
4. **Direction** (`direction-*`).
   - `projects` imports nothing from `links` or `service-desk` (ADR 0024).
   - `activity` and `notifications` import no business module except through its `schema.ts`
     (ADR 0009, ADR 0040).
   - `assets`, `service-desk`, `projects` and `knowledge` do not import each other; what crosses
     goes through `links` or `shared/events.ts`.
   - `directory` imports no business module except `activity`.
   - `auth`, `access`, `db`, `shared` and `settings` (infrastructure) import no business module,
     except `directory`'s `index.ts` and `schema.ts` and, in `db/schema.ts`, every module's
     `schema.ts` (`direction-infrastructure`); specs and `testing/` folders follow rule 6.
5. **Routes** (`routes-no-db`, `routes-no-schema`). Non-spec files under `src/routes/` import no
   `db` module at runtime (a type-only edge such as `import type { Transaction }` queries nothing)
   and no `*/schema.ts` at all.
6. **Specs and fixtures** (`testing-in-production`, and rule 1 for the rest). Specs and `testing/`
   folders may import anything in their own module, plus the `index.ts`, the `schema.ts` and the
   `testing/` folder of any module, but never another module's internal files. No other file
   imports a `testing/` folder.
7. **No runtime cycles** (`no-circular`). Over `src/`, excluding `src/lib/components/ui/**`
   (vendored shadcn-svelte, regenerated by its CLI) and specs. A cycle counts only when every edge
   of it is a runtime edge (`viaOnly: { dependencyTypesNot: ['type-only'] }`), because TypeScript
   erases type-only edges.

### Baseline

`.dependency-cruiser-known-violations.json` records what already violated the rules when this ADR
landed, so the rules can be `error` from day one. The policy:

- `--ignore-known` is always on; there is no "warn" tier.
- **An entry is never added without a justification in the pull request**, and each group is listed
  with the issue or change that removes it in a comment at the top of `.dependency-cruiser.cjs`.
- Entries are removed, never rewritten: when a violation is fixed, regenerate with
  `depcruise-baseline` and the file shrinks. A stale entry is a signal to delete it.
- A fix that would close a runtime cycle or needs a product or architecture decision goes to the
  baseline rather than being improvised.

### Known limits

- **`auth` imports `assets` and `projects`** (`auth/provision.ts`). An infrastructure → domain
  inversion, tracked in #354; an "infrastructure imports no domain" rule now would only grow the
  baseline.
- **Type-only cycles** (`notifications/follows ↔ notify`, `projects/tasks ↔ members`, …) are
  allowed: they have no runtime effect.
- **Type-only imports in `.svelte` files are invisible.** dependency-cruiser compiles Svelte to
  JavaScript before reading imports, which erases `import type`, so a deep type import from a
  component (for example `#lib/server/links/related.js`) is not reported. Runtime imports are
  seen, and SvelteKit already refuses runtime `$lib/server` imports from client code at build
  time. Components import server types through the domain barrel (`<module>/index.js`); no
  second enforcement mechanism is added.
- Only the rules above are encoded. There is no whitelist of every allowed module edge: a new edge
  that breaks no rule needs no config change.

## Alternatives considered

- **`eslint-plugin-boundaries`.** Rejected: it needs an extra resolver to follow `#lib/…`, has no
  cycle detection, and works file by file, so it cannot see a cycle closed from an unchanged file.
- **One generated ESLint block** (fixing the "blocks replace each other" defect by building the
  patterns from a list). Rejected: it still matches import text, still cannot tell a table from a
  function re-exported by a barrel, and still has no graph view.
- **A full allowlist of module → module edges.** Rejected: every new legitimate edge would be a
  config change, which is constant friction for a monolith that is still moving, and the failures
  it prevents are already covered by the direction rules.

## Consequences

- `eslint.config.js` loses every `no-restricted-imports` block, `NOTIFICATIONS_TABLES` and
  `BARREL_TABLES`.
- The whole server graph is checked on every `npm run lint`, in CI too, without the lint cache.
  The run takes a few seconds on the full `src/` tree.
- Because barrels carry no tables, code that needs a table imports `<m>/schema` explicitly. That
  makes every table dependency visible in the import list, and rule 2 judges it.
- `links ↔ service-desk` and `DataTable ↔ DataTableSkeleton` are known cycles, baselined until
  they are broken.
